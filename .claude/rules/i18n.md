# Languages (i18n)

The languages are in `Services/AppLanguages.All`. The app and the website's home page (`site/home/<code>.json`,
`discoverability.md`) are translated; the user guide is in English, and so are the AI tools' own texts (instructions,
descriptions, schemas, answers).

## The language in use

- Settings › General › **Language**: "Use system language" (`AppSettings.Language` null, the default and in older files)
  or a language. Changing it asks to restart PuppyMacro.
- `App.ApplyLanguage`, once at start, before any window, for every thread: the texts' language is Windows' display
  language when translated, its parent too, Portuguese gives pt-BR, otherwise English; numbers and dates use Windows'
  regional format while it is in the same language, otherwise the language's usual one, with Gregorian dates. It also
  sets `FrameworkElement.Language`, without which WPF formats bindings in en-US.
- `PUPPYMACRO_LANGUAGE` (development build only) forces a language at start: the end-to-end tests and the screenshots
  use English.

## Texts

- **No text for the user written in the XAML**, checked by `ResourcesTests` (`Every_text_of_the_xaml_comes_from_the_resources`):
  a text attribute or a `TextBlock` / `Run` text is a markup extension (`{x:Static r:Strings.…}`, a binding), a global word,
  a single letter or digit, or F1 to F24, else the test fails. Key caps take the key's translated name (`Keys_Ctrl`,
  `Keys_Delete`: "Strg", "Entf" in German), as everywhere else. The C# has no such test: the rule and the review hold there.
- **How texts are written.** Every text the user reads (labels, notes, errors, tooltips, dialogs) is a natural sentence,
  the way a person would say it: what happened and what the user can do next. No pieces glued with colons, no shorthand
  ("No key: choose one with Edit"), no internal names (Source, Vk, AppExe). Short where space is short (the Import window's
  notes, a card's line), but still a sentence. The AI tools' own texts (English, for the model) are not covered.
- **Every translation, wherever the project has one (the app, the home page, any other translated text), says what the
  English means the way a native speaker would say it, never word for word.** Before using a phrase, check on the internet
  that in that language it really conveys that concept: how native sites, Microsoft and apps of the same kind say it. When
  the literal sentence sounds unnatural, build it again (another order, another verb, two sentences), keeping the
  placeholders, the Windows terms and the global words. The home page uses the app's own words for its features, settings
  and keys (`Strings.<code>.resx`) and writes numbers and units as the app does in that language. Avoid forms that would need the gender or number of a placeholder or
  of an item kind the sentence does not know ("quindi il tasto di scelta rapida non viene importato", not "viene importato/a
  senza…").
- **No text for the user in code or XAML.** `Resources/Strings.resx` holds the English texts; `Strings.<code>.resx` the
  translations (`it`, `pt-BR`, `zh-Hans`…, satellite assemblies). MSBuild writes the public class `Strings` from
  `Strings.resx` before the XAML is compiled (`GenerateStringsClass` in the csproj): XAML uses
  `{x:Static r:Strings.Key}` (`xmlns:r="clr-namespace:PuppyMacro.Resources"`), C# `Strings.Key`.
- Keys: `Area_Name` (`Loops_Add`, `MacroEditor_Record`). A sentence with values is **one key with placeholders**
  (`string.Format(CultureInfo.CurrentCulture, Strings.Remaps_DeleteConfirm, a, b)`), never pieces glued together: word
  order changes between languages. An enum shown to the user maps each value to a key, never `ToString()`. Lists join
  with `Strings.ListSeparator`. A `<comment>` says what each placeholder is.
- **Counts**: `Plurals.Format("Key", count, …)` with `Key_one`, `Key_other`… Each language has its CLDR forms
  (`Plurals.Category`, `Plurals.RequiredForms`).
- Numbers and dates for the user: `CultureInfo.CurrentCulture`; in files and JSON: `InvariantCulture`, so a backup is the
  same on every PC whatever its language.
- **Global words: never translated.** Some words are the same in every language: names, brands, terms the user wants
  kept as they are. They are not necessarily English (a name like "pasta" stays "pasta" in Japanese too). Examples:
  "AI" in the side rail and as the AI page's title, product names such as PuppyMacro or MCP.
  - Which words are global is the user's decision: when a word looks global (a name, an acronym, a brand, a term
    written the same way in many languages), **ask the user** before treating it as global or translating it. Do not
    list them in the rules: the code holds them.
  - A label that is only a global word: its key is only in `Strings.resx` (its `<comment>` starts with "GLOBAL") and in
    `ResourcesTests.Global`; no `Strings.<code>.resx` has it, so every language shows the same text, and
    `ResourcesTests` fails if a translation adds it.
  - Inside translated sentences a global word is written exactly as it is, never translated or transliterated.
- Not translated: the macros' Debug log (`RunLog`: always English, so it can be pasted anywhere, in a chat too; the
  user's choice; its card and window are translated), data (names of loops, macros, remaps, apps), JSON field names and
  values, the Code view schema's descriptions (`CodeSchema`, read by AI apps too), the development build's samples, keys
  written on the keyboard in shortcut lists, Monaco's own menus.
- **Every new or changed text is translated into every language in the same pull request** (checked by
  `ResourcesTests`).
- Translations follow the terms Windows uses in that language (Settings, Microsoft's terminology). When a term is
  uncertain, look it up (Microsoft Terminology, Windows in that language) instead of guessing.
- A new language: its line in `AppLanguages.All` (code and own name), its `Strings.<code>.resx`, its plural rule in
  `Plurals` when it has new forms, its cases in `LanguageTests`; for the home page its `site/home/<code>.json`, its line
  in `$HomeLanguages` of `scripts/site.ps1` and its flag in `site/assets/flags` (`discoverability.md`).

## Texts kept in files

- History versions (`HistoryVersion.SummaryPhrase`, `ChangePhrases`) and AI requests (`AiActivity.RequestPhrase`) keep
  their texts as a `Phrase` (resource key and arguments, keys named at display), shown in the language of the moment,
  next to the English text (`Summary`, `Changes`, `Request`) that older versions read. Files from before 1.17 have only
  the English text, which is shown as it is; so is a phrase whose key this version does not have.
- The History keeps "You" (`ItemHistory.You`) in the file and shows it translated.

## AI apps

- Everything runs in the user's language, also an AI app's tool calls and the UI work they do (the windows it opens,
  the cards a save refreshes). The texts an AI app receives are English: the AI tools' own texts are English constants,
  and the texts that come from code shared with the UI (the Code views' checks, hotkey conflicts, key names, what
  changed) are made with `Loc.English(...)` where `AiTools` gives them to the AI app. A new tool that returns such a
  text wraps it the same way.
- What the user sees of an AI request (confirmations, the activity) uses the user's language: `AiTools` builds it from
  `Strings` / `Phrase`, with one key per kind of item (`Ai_Deleted_loop`, `Ai_Deleted_macro`…), as languages say
  "deleted loop" and "deleted macro" differently.

## Right to left

- Arabic runs right to left (`FlowDirection` from the texts' culture, set on every window). What stays left to right:
  the Code view, key names and key caps, coordinates, numbers in fields, and the overlays drawn over other apps (their
  positions are the screen's).
